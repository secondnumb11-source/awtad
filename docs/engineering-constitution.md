# دستور أوتاد الهندسي الإلزامي

## 1. قاعدة الصفر
هذا الفرع هو إعادة بناء مستقلة من الصفر. لا يُعتد بأي كود أو اختبار أو نتيجة أو مرحلة من محاولات أو إصدارات سابقة كدليل لصحة البناء الحالي.

## 2. حظر البناء العشوائي
يحظر منعًا باتًا:
- كتابة ميزات خارج المرحلة المعتمدة.
- إنشاء ملفات أو جداول أو APIs لمجرد زيادة حجم المشروع.
- الانتقال إلى مرحلة جديدة قبل إغلاق جميع بوابات المرحلة الحالية.
- اعتبار وجود الكود أو نجاح `build` وحده دليلًا على عمل الميزة.
- استخدام mock أو stub أو بيانات وهمية لإخفاء فشل وظيفة يفترض أن تكون حقيقية.
- الادعاء بأن تكاملًا حكوميًا أو مصرفيًا أو محاسبيًا يعمل دون وجود مواصفة/واجهة رسمية واختبار موثق.

## 3. دورة كل مرحلة
كل مرحلة تمر بالترتيب:
1. تحديد نطاقها وقبولها.
2. التصميم قبل التنفيذ.
3. التنفيذ فقط داخل النطاق.
4. اختبار الوحدة.
5. اختبار التكامل.
6. اختبار API عند وجود API.
7. اختبار قاعدة البيانات عند وجود DB.
8. اختبار E2E عند وجود رحلة مستخدم.
9. اختبار الصلاحيات والعزل الأمني.
10. فحص الأخطاء والثغرات.
11. إصلاح جميع الأخطاء المكتشفة.
12. إعادة تشغيل الاختبارات بعد الإصلاح.
13. توثيق النتيجة على نفس commit الذي تم اختباره.
14. فقط عند PASS يمكن بدء المرحلة التالية.

## 4. حظر ترك الأخطاء
يحظر ترك خطأ معروف أو تحذير أمني مؤثر أو فشل اختبار دون:
- تحديد السبب.
- تسجيله.
- إصلاحه أو إثبات أنه خارج النطاق بمبرر موثق.
- إعادة الاختبار بعد الإصلاح.

أي فشل غير مغلق يجعل المرحلة INCOMPLETE/FAILED ولا يسمح بالانتقال.

## 5. قاعدة الدليل
لا تعتبر الميزة مكتملة إلا بدليل قابل لإعادة التنفيذ على النسخة الحالية:
- commit SHA محدد.
- بيئة اختبار محددة.
- أمر/اختبار محدد.
- نتيجة فعلية.
- مسار نجاح وفشل عند الحاجة.

## 6. الأمن والصلاحيات
الأمان جزء من الوظيفة وليس مرحلة تجميلية:
- فصل authentication عن authorization.
- عزل المستأجرين/المنشآت.
- RBAC/ABAC حسب الحاجة.
- منع الوصول المباشر عبر API عند عدم امتلاك الصلاحية.
- audit trail للعمليات الحساسة.
- عدم وضع أسرار أو مفاتيح حقيقية في المستودع أو الكود.
- عدم السماح للذكاء الاصطناعي بتجاوز الصلاحيات أو قواعد العمل.

## 7. قاعدة البيانات
أي schema يجب أن يبدأ من migration نظيفة وقابلة لإعادة البناء من الصفر، مع:
- القيود والعلاقات.
- الفهارس اللازمة.
- RLS/authorization حيث يلزم.
- اختبارات العزل بين المنشآت.
- اختبارات العمليات المتزامنة والقيود المهمة.

## 8. التكاملات
لا توجد تكاملات وهمية معلنة كتكاملات حقيقية. كل تكامل له adapter/interface واضح، ومواصفة مصدرية، واختبار نجاح وفشل. إذا لم تتوفر الواجهة الرسمية، يبقى التكامل في حالة PLANNED/ADAPTER-READY وليس LIVE.

## 9. الإصدار
لا Merge ولا Release ولا إعلان "مكتمل" قبل اجتياز بوابات الجودة للمرحلة الحالية على نفس النسخة.

## 10. المخالفات
أي مخالفة لهذا الدستور توقف التنفيذ في المرحلة الحالية وتعيدها إلى INCOMPLETE حتى تتم معالجة المخالفة وإعادة الاختبار.

## 11. أولوية الجودة
القاعدة: ميزة واحدة تعمل فعليًا أفضل من عشر ميزات غير مكتملة. لا نطارد عدد الملفات أو سرعة البناء على حساب صحة النظام.
