# دستور أوتاد الهندسي

هذا المستند قاعدة قبول إلزامية لكل مرحلة من مراحل بناء أوتاد، ولا تُعد أي مرحلة منتهية أو ناجحة لمجرد اكتمال كتابة الملفات.

## 1. تعريف النجاح

لا تُعلن المرحلة «مكتملة» إلا بعد تحقق جميع البوابات التالية على نفس الحالة البرمجية التي سيُبنى عليها الإصدار:

1. فحص المصدر والبنية والملفات المطلوبة.
2. تثبيت الاعتماديات بنجاح باستخدام lockfile ثابت.
3. TypeScript بدون أخطاء.
4. ESLint بدون أخطاء.
5. اختبارات الوحدة والمنطق.
6. اختبارات التكامل وطبقة البيانات عند ارتباط المرحلة بقاعدة البيانات.
7. تطبيق migrations على قاعدة اختبار نظيفة، ثم التحقق من schema والقيود وRLS.
8. بناء Production بنجاح.
9. تشغيل Production build والتحقق من startup.
10. Health check فعلي.
11. اختبارات API الحرجة.
12. اختبارات E2E للرحلات التي أضافتها المرحلة.
13. فحوصات الأمن والعزل بين المستأجرين والصلاحيات، بما في ذلك مراجعة RLS والسياسات.
14. مراجعة عدم وجود secrets أو مفاتيح حقيقية أو بيانات اعتماد داخل المستودع.
15. مراجعة عدم وجود تكاملات حكومية أو خارجية وهمية؛ أي تكامل غير موثق يُبنى خلف adapter/interface واضح ويظل غير نشط حتى تتوفر مواصفات رسمية قابلة للتحقق.

## 2. قاعدة عدم الادعاء

- «الكود موجود» لا يعني «الكود يعمل».
- «CI أخضر سابقاً» لا يعني أن النسخة الحالية خضراء بعد أي تعديل.
- «Build ناجح» لا يعني أن runtime يعمل.
- «Migration موجودة» لا تعني أنها طبقت بنجاح على قاعدة نظيفة.
- «API موجود» لا يعني أن المصادقة والصلاحيات والعزل صحيحة.
- عند تعذر تنفيذ أي بوابة، تُسجل الحالة صراحة كـ UNVERIFIED ولا تُعلن المرحلة ناجحة.

## 3. التحقق على نفس الإصدار

يجب أن يكون التحقق مرتبطاً بـ commit SHA محدد. إذا تغير الكود بعد آخر CI/Build/Runtime check، يجب إعادة البوابات المتأثرة على الـ commit الجديد.

## 4. قاعدة قاعدة البيانات

كل مرحلة تضيف schema يجب أن تتضمن:
- migration قابلة لإعادة البناء على قاعدة نظيفة.
- اختبارات constraints وforeign keys والفهارس المهمة.
- RLS وسياسات الوصول المناسبة.
- اختبار عدم الوصول بين المؤسسات.
- اختبار صلاحيات الدور/النطاق.
- عدم استخدام بيانات إنتاج حقيقية في الاختبارات.

## 5. قاعدة الأمن

- لا تُحفظ أسرار حقيقية في الكود أو Git.
- أي secret ظهر في المحادثة أو الملفات يُعامل كمُعرّض للخطر ولا يُعاد استخدامه.
- المصادقة والتحقق من هوية المستخدم منفصلان عن authorization.
- authorization يجب أن يكون server-side وقابلاً للتدقيق.
- AI لا يتجاوز الصلاحيات؛ كل أداة/وكيل يمر عبر permission check وbusiness rules وaudit.

## 6. قاعدة التغييرات

بعد كل تعديل جوهري:
- شغّل البوابات المتأثرة.
- لا تستخدم نتيجة قديمة لتبرير نتيجة جديدة.
- أصلح الفشل قبل الانتقال للمرحلة التالية.

## 7. بوابة المرحلة

الحالة الوحيدة المسموح بها عند الإعلان عن النجاح هي:

PASS = source + dependencies + typecheck + lint + tests + migrations/data checks + production build + runtime + API/E2E + security

أي عنصر غير متحقق منه يجعل الحالة INCOMPLETE/UNVERIFIED.

## 8. السجل

يجب أن تسجل كل مرحلة:
- commit SHA.
- نتائج كل بوابة.
- قاعدة الاختبار المستخدمة.
- أي تحذيرات أمنية معروفة.
- ما لم يمكن التحقق منه.

هذا الدستور يُطبق على جميع مراحل أوتاد الحالية والقادمة.
